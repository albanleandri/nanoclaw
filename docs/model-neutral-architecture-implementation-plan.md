# Model-Neutral Architecture Implementation Plan

Date: 2026-06-21

## Goal

Implement the model-neutral architecture direction described in `docs/model-neutral-architecture-assessment.md` through small, reversible changes. Start with low-risk documentation, static verification, and instruction normalization before changing schedule ownership or setup flows.

## Strategy

The safest path is to reduce accidental provider lock-in before changing execution semantics:

1. First make assumptions visible.
2. Then make provider-neutral paths and contracts explicit.
3. Then rewrite prompts and skill instructions where the runtime already supports the neutral behavior.
4. Only after that, replace hard-coded schedule ownership and setup provider selection.

This order avoids breaking the working Claude/Telegram path while making Codex and future providers steadily more viable.

## Full Scope

The implementation covers every surface where provider coupling can affect current container/custom capabilities or scheduled tasks:

- **Runtime contract:** session DB rows, outbound system actions, MCP tools, and `AgentProvider` dispatch.
- **Provider adapters:** Claude SDK behavior, Codex app-server behavior, auth/continuation state, sandbox/approval handling, and generated provider-native docs.
- **Custom skills:** active `SKILL.md` files, instruction files, custom agents, helper scripts, and skill-level docs under `container/skills/custom`.
- **Shared resources:** mounted `knowledge`, `trading-scripts`, `trading-data`, `research-notes`, and `docs` resources selected by both Pinova groups.
- **Scheduled tasks:** active `pending`/`paused` task rows, their prompts/scripts, recurrence metadata, owner session DBs, and admin/list/update behavior.
- **Setup and operations:** first-run provider choice, credentials, verification, handoff/recovery behavior, and operator docs.
- **Channel assumptions:** Telegram-specific routing or pool behavior when it is intentionally part of a task or skill.

The plan does not include migrating the runner away from Bun, replacing `@anthropic-ai/claude-agent-sdk`, redesigning channel adapters, duplicating recurring schedules into Codex-owned sessions, or converting every provider-specific workflow into a generic abstraction. Provider-specific capabilities remain acceptable when they are named, documented, and tested as such.

## Prioritization Principles

- **Low risk first:** documentation, static checks, and generated reports before DB migrations or setup changes.
- **No duplicate schedules:** never copy recurring task rows into a second provider-owned session.
- **Preserve Claude compatibility:** keep `/workspace/group` and `/home/node/.claude/skills` working as compatibility paths until replacement paths are proven.
- **Prefer additive checks:** warn first, fail later after false positives are understood.
- **Keep each slice independently reviewable:** each phase should have a clear rollback path.

## Phase 6: Live Scheduled Task Prompt Migration

Risk: moderate to high.

Objective: update live task prompts in place while preserving series IDs, recurrence, and single-owner execution.

Prerequisites:

- Phase 0 inventory exists.
- Phase 3 verifier exists.
- Phase 5 shared path normalization is complete.
- A fresh backup exists.

Implementation targets:

- `scripts/export-scheduled-tasks.ts` or a documented `scripts/q.ts --readonly` command for export.
- `scripts/migrate-scheduled-task-prompts.ts` only if tool-based `update_task` is too error-prone for batch edits.
- Owner session DB: `data/v2-sessions/<owner-agent-group-id>/<session-id>/inbound.db`.
- Handoff/update docs: this file plus `docs/HANDOFF.local.md`.

Tasks:

- [ ] Back up all databases with `pnpm run backup`.
- [ ] Export current active task rows to a markdown/JSON review file.
- [ ] Include these fields in the export:
  - `series_id`
  - live row `id`
  - `status`
  - `process_after`
  - `recurrence`
  - parsed `prompt`
  - parsed `script`
  - routing fields (`platform_id`, `channel_type`, `thread_id`)
  - detected portability warnings from the verifier
- [ ] For each task, classify:
  - no change needed
  - path rewrite only
  - provider tool rewrite
  - channel-specific but acceptable
  - provider-specific by design
- [ ] Create a per-task migration manifest:

```json
[
  {
    "seriesId": "task-...",
    "risk": "path-rewrite-only",
    "oldPromptHash": "sha256:...",
    "newPrompt": "...",
    "newScript": null,
    "expectedRecurrence": "0 7 * * *",
    "notes": "Replaced /home/node/.claude/skills path with /app/skills/custom path."
  }
]
```

- [ ] Rewrite low-risk prompts first:
  - replace `/workspace/group` with `/workspace/agent` or `/app/shared/*` where equivalent
  - replace `.claude` script source paths with `/app/skills/custom/*` where equivalent
  - keep `bot_index` only when Telegram pool delivery is the intended behavior
- [ ] Apply changes with one of two allowed paths:
  - preferred interactive path: call `update_task` for each series through the owner/admin agent and verify after each update
  - controlled maintenance path: a host-side script opens only the owner `inbound.db`, matches rows by `series_id`, verifies `oldPromptHash`, updates only `content`, and leaves `id`, `series_id`, `recurrence`, `process_after`, and routing fields unchanged unless explicitly specified in the manifest
- [ ] Re-run `list_tasks` from the owner and admin groups.
- [ ] For each migrated task, record before/after prompt hash, command used, and verification result in the export report.

Edge cases to handle:

- Multiple live rows with the same `series_id` should be treated as an error unless they represent a known paused/pending conflict; do not update blindly.
- Completed historical rows should not be rewritten; only live `pending`/`paused` rows should change.
- `script` values can contain quotes, newlines, and JSON. Update through structured JSON parsing, not string replacement.
- If a task currently uses a Claude-only `Task` subagent, do not rewrite it in this phase unless a provider-neutral replacement exists. Mark it `provider-specific` or defer to Phase 8.
- If a task sends to `bot_index`, preserve it unless the migration explicitly changes channel behavior.

Success criteria:

- Active task count remains unchanged unless a task is intentionally cancelled.
- Every migrated task keeps its original `series_id`.
- Pinova Codex can list the same owner schedule.
- The next due occurrence for a migrated task wakes only the owner session once.
- Re-running the migration manifest is idempotent: already-migrated rows are skipped by hash or reported as unchanged.

Verification:

```bash

pnpm exec tsx scripts/q.ts --readonly data/v2-sessions/<owner>/<session>/inbound.db "SELECT series_id, status, process_after, recurrence, content FROM messages_in WHERE kind='task' AND status IN ('pending','paused')"
pnpm exec tsx scripts/check-model-neutrality.ts --readonly --warn-only
pnpm exec vitest run src/modules/scheduling/actions.test.ts
```

Rollback:

- Restore from backup, or apply the exported original task prompts back with `update_task`.
- If using the maintenance script, rollback should use the same manifest shape with `oldPrompt` as the target and the migrated prompt hash as the guard.

## Phase 7: Generic Schedule Ownership

Risk: moderate to high.

Objective: replace hard-coded Pinova schedule sharing with DB-backed schedule owner/admin grants.

Implementation targets:

- Migration: `src/db/migrations/<next>-schedule-admin-grants.ts`.
- DB helper: `src/db/schedule-admin-grants.ts`.
- Runtime resolver: either `src/modules/scheduling/ownership.ts` or internal helpers in `src/modules/scheduling/actions.ts`.
- Tests: `src/modules/scheduling/actions.test.ts` plus focused DB helper tests.
- CLI/admin surface, if needed: `src/cli/resources/schedule-admin-grants.ts` or a narrower group config command.

Schema:

```sql
CREATE TABLE schedule_admin_grants (
  admin_agent_group_id TEXT NOT NULL REFERENCES agent_groups(id) ON DELETE CASCADE,
  owner_agent_group_id TEXT NOT NULL REFERENCES agent_groups(id) ON DELETE CASCADE,
  created_at TEXT NOT NULL,
  created_by TEXT,
  PRIMARY KEY (admin_agent_group_id, owner_agent_group_id)
);

CREATE INDEX idx_schedule_admin_grants_owner
  ON schedule_admin_grants(owner_agent_group_id);
```

Resolution algorithm:

1. If caller has no grant rows, use caller's own session DB.
2. If caller has exactly one grant, resolve that owner group.
3. If caller has multiple grants, require an explicit owner selector for mutating actions; `list_tasks` may list grouped output by owner.
4. Resolve the owner session by:
   - prefer active sessions for the owner group with live task rows
   - otherwise use the newest active owner session
   - if no owner session exists, return a structured host error to the caller
5. Open only the resolved owner `inbound.db` for task administration.

Tasks:

- [ ] Add a central migration for `schedule_admin_grants`.
- [ ] Add DB helpers:
  - grant admin access
  - revoke admin access
  - list grants
  - resolve schedule owner for a session
- [ ] Replace `PINOVA_AGENT_GROUP_ID` and `PINOVA_CODEX_AGENT_GROUP_ID` in `src/modules/scheduling/actions.ts`.
- [ ] Seed the current Pinova Codex -> Pinova Claude grant through a migration, setup script, or local operator command.
- [ ] Update `list_tasks`, `pause_task`, `resume_task`, `cancel_task`, and `update_task` tests for arbitrary groups.
- [ ] Decide whether `schedule_task` can target an owner schedule explicitly; if yes, require grant validation.
- [ ] Extend scheduling MCP schemas only if explicit owner selection is needed:

```typescript
{
  ownerAgentGroupId?: string; // optional for list; required for mutation when caller has multiple grants
}
```

- [ ] Return structured system-action errors for:
  - unknown owner group
  - no grant for owner
  - multiple possible owners and no owner selected
  - owner has no active session
  - owner session DB missing
- [ ] Add an operator-visible way to inspect grants before enabling mutation from non-owner groups.

Test cases:

- Caller without grants lists/mutates only its own session schedule.
- Caller with one grant lists owner tasks and does not see a duplicate local task.
- Caller with one grant pauses/resumes/cancels/updates owner task rows only.
- Caller with multiple grants gets grouped list output and must specify owner for mutation.
- Unauthorized caller cannot mutate another group's schedule by passing an owner ID.
- Missing owner session produces an error response and does not create task rows.
- Recurrence fanout still occurs only in the owner session after an admin-originated update.

Success criteria:

- Existing Pinova shared schedule administration still works.
- Tests prove arbitrary admin/owner group pairs work.
- No hard-coded local agent group IDs remain in scheduling runtime code.
- Codex administration still does not create Codex-owned duplicate recurring rows.
- The grant model is inspectable and revocable.

Verification:

```bash
pnpm exec vitest run src/modules/scheduling/actions.test.ts src/modules/scheduling/db.test.ts
pnpm exec vitest run src/db
pnpm run typecheck
pnpm test
```

Rollback:

- Revert migration/code and restore previous scheduling actions only if no new grants have been used.
- If grants have been used, rollback needs a DB migration down plan or backup restore.

Decision B: Polymarket evaluator.

Two acceptable end states:

- **Provider-specific:** Polymarket remains Anthropic-backed. Skill header says so. Verifier allowlist records the reason.

Configuration should select evaluator provider/model without changing discovery, cache, outcome, metrics, or reporting code.

Design requirements:

- Runtime provider and development assistant are separate concepts.
- Claude remains the default provider unless the user chooses otherwise.

| Future provider | provider skill supplies auth/setup contract | provider-specific mount/env from registry | provider skill test command |

- Do not replace the Claude provider's `@anthropic-ai/claude-agent-sdk`.
- Do not remove Claude Code setup recovery.
- Do not convert Telegram-specific delivery into a generic channel abstraction in this work.
