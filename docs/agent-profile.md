# Agent Profile

NanoClaw separates durable agent identity from provider execution details with a derived `agentProfile` object.

The profile is generated by the host from the existing agent group row plus `container_configs`. It is embedded in the materialized `groups/<folder>/container.json` at spawn time. The container mounts that file read-only at `/workspace/agent/container.json` and `/workspace/group/container.json`.

The profile is intentionally derived state. There is no separate DB table or migration for it.

## Responsibilities

### Agent group

An agent group is the durable user-facing agent identity:

- central DB row in `agent_groups`
- stable group id and folder
- display name
- persistent workspace under `groups/<folder>/`
- channel/session wiring through `messaging_group_agents`

Multiple sessions can use the same agent group. Those sessions share the group workspace but have separate session DBs.

### Agent profile

An agent profile is the provider-neutral runtime description derived for that group:

- `agentGroupId`
- `groupName`
- `assistantName`
- memory/workspace conventions
- selected skills
- MCP server definitions
- CLI scope
- selected shared resources

The profile is used by host-side composition code and is available to the runner for introspection and future providers. Providers do not yet depend on it directly; existing top-level `container.json` fields remain compatible.

### Provider adapter

A provider adapter owns SDK/runtime-specific behavior:

- Claude-like runners keep Claude-specific state and tool policy inside the Claude provider.
- Codex-like runners keep Codex-specific project docs, auth mounts, sandbox, and size-cap behavior inside the Codex provider.
- Future providers should read the same top-level config/profile intent and translate it into their own runtime constraints.

The provider adapter should not be the source of truth for group identity, memory paths, skills, shared resources, or MCP declarations.

### Model selection

Provider and model are separate:

- `container_configs.provider` selects the adapter unless overridden by `sessions.agent_provider`.
- `container_configs.model` and `container_configs.effort` are passed through as provider settings.
- The agent group name and assistant name are identity/role fields, not model fields.

Provider resolution order is:

1. session provider override
2. container config provider
3. Claude default

## Runtime Files

NanoClaw still emits provider-native instruction files because providers load context differently.

| File | Purpose |
| --- | --- |
| `container.json` | Materialized runtime config plus neutral `agentProfile`. |
| `CLAUDE.md` | Generated Claude project doc. Imports the runtime contract and enabled fragments. |
| `CLAUDE.local.md` | Per-group Claude-compatible local memory/instructions. |
| `AGENTS.md` | Generated Codex project doc. Renders compatible runtime sections within Codex's project-doc cap. |
| `.claude-fragments/` | Generated Claude import fragments for skills, modules, and MCP instructions. |

`CLAUDE.md` and `AGENTS.md` are generated compatibility artifacts. Do not edit them directly. Put durable group-specific instructions in the provider-neutral workspace where possible, or in the provider-specific local file when the provider requires it.

## Workspace Conventions

`/workspace/agent` is the canonical persistent agent workspace inside the container.

`/workspace/group` is a legacy alias for the same group folder and remains mounted for compatibility with existing skills and scheduled tasks.

Session-specific state lives under `/workspace` outside the group workspace:

- `inbound.db`
- `outbound.db`
- `.heartbeat`
- `outbox/`
- provider session state mounted by each provider

Shared resources are selected by `container_configs.shared_resources` and linked into the group workspace under `shared/`. The backing mounts are provider-neutral:

- `/app/shared/<resource>`
- `/app/docs` for docs

## Current Compatibility Rules

- `CLAUDE.md` remains generated for Claude-compatible runners.
- `AGENTS.md` remains generated for Codex-compatible runners.
- `/workspace/agent` remains canonical for durable group workspace state.
- `/workspace/group` remains a legacy alias.
- `container.json` keeps existing top-level fields while also embedding `agentProfile`.
- Providers must continue to tolerate missing `agentProfile` for old generated configs.

## Extension Guidance

When adding a provider:

1. Add a provider adapter that translates NanoClaw intent into the provider runtime.
2. Reuse `AgentProfile` and `InstructionSection` collection where possible.
3. Generate provider-native instruction files at the edge.
4. Keep provider-specific auth, sandbox, continuation, and state directories in the provider adapter.
5. Avoid introducing provider names into group/workspace conventions unless the provider requires them.
